Audit base: RapidRoom `f7805a7e35116b79edb5447e490d896ec269db44`. This table compares field handling, not visual equivalence or Adobe application compatibility. Sidecar and preset contexts differ: presets are partial edits, photos may describe complete edits. Explicit zero must remain distinct from an omitted field.

## Small fixes in this PR

Read scalar/list/language/qualified properties with the existing bounded XML reader instead of literal-prefix regexes. Resolve namespace bindings, restrict properties to the image's RDF subject, preserve first-property precedence, and keep nested profile/mask fields out. Attributes, elements, quoted whitespace and XML references decode consistently. Curve lists reject an invalid item rather than silently importing only valid points. Preset names prefer the `x-default` language; nested profile requirements do not become photo/preset requirements. Correct `HighlightRecovery` classification to match the converter's actual legacy key.

Existing canonical unbound `crs`/`rdf` fragments remain accepted for legacy inputs; an explicitly wrong namespace binding is never treated as CRS. The new reader does not claim full RDF graph support. Profile look curves are read in a separate namespace-aware resource scope; other mask/profile payloads still have limitations, documented below.

## Parser and writer safety

RapidRoom's shared XML reader caps UTF-8 input at 16 MiB, depth at 64 and nodes at 200,000. It rejects DOCTYPE before parsing (including incomplete declarations) and again at XML events; unknown entity references are not expanded. It never resolves external resources. The new converter regression sends a SYSTEM entity packet through the actual entry point and expects refusal.

Metadata updates use span replacement, preserving unowned namespace properties, nested structures, comments and CDATA byte for byte. Tests cover namespace collisions and same-subject descriptions. The converter-to-writer integration regression preserves a CRS exposure and foreign CDATA exactly while changing a rating, then re-imports the exposure. File-level metadata writes preserve malformed backups or refuse unsafe input; they do not justify an Adobe develop-settings writer. PR210's photo-edit payload writer remains unmerged pending real Lightroom acceptance.

## Remaining gaps and limits

- #214: Complete-photo defaults and partial presets need different policies. AutoShade's observed absent-key defaults include RAW Sharpness 40, ColorNoiseReduction 25, radius 1, detail 25, noise companions 50, grain size 25/frequency 50, vignette midpoint/feather 50, grading blend 50 and curve splits 25/50/75. Do not insert those into sparse presets or replace explicit zero; rendering scales still need #159 calibration.
- #215: Parametric CRS values/splits are not imported. Native rendering consumes baked point curves, so copying UI `parametricCurve` state alone would do nothing. A future implementation must combine point and parametric curves and preserve compatible UI state.
- #216: Unsupported global settings have no complete per-setting import report. Existing categories cover masks/profile/WB/AI/Point Color; fields such as detail companions, calibration, transforms, lens manual corrections and retouch can otherwise disappear silently.
- Legacy masks, range masks, healing, lens blur, physical/named WB and calibration/transform operators are larger gaps, not small field aliases. Existing #31/#33/#88/#159 and pending #173/#177/#185 remain the associated work.
- Mask and profile colour-table parsing still have gaps; renamed-prefix support here covers top-level scalars, curve lists and scoped look curves, not every nested mask/profile representation. Qualified values without a simple rdf:value are ignored. RDF graph references/reification are outside this reader.
- No private Lightroom file is committed and no real Adobe application test is claimed. The external apps explicitly describe their mappings as approximations; they are cross-checks, not an oracle for renderer response.

Renamed TIFF/EXIF dimensions/orientation, mask structures, profile colour tables and complete structured-value reporting are not fixed by the top-level CRS reader. Imported numeric settings can still be an approximation. These are explicit scope limits, not a statement that every XMP representation is now interchangeable.

Additional policy follow-up #218: prevent double application of already-baked photo development data while preserving metadata-only imports and distinguishing reusable presets.

The native point-curve representation is limited to 16 control points in the render uniform. Import/render reporting should disclose or deliberately resample denser foreign curves rather than imply that every stored point reaches the renderer (#215/#216). Qualified scalar support here covers direct `rdf:value` and `rdf:Description` resources; typed RDF node/reification forms remain outside the reader.

Cross-source disagreement is explicit: RAWmakase `src/xmp/local.rs::adjustments` takes LocalExposure2012 directly as EV, while AutoShade and LightCraft multiply its file value by four; keep our existing ×4 rather than treating a second implementation as an oracle. RAWmakase corroborates LocalHue ×180 and normalizes global Sharpness to an internal 0–1 range by /150. Different internal units are not a reason to copy a slider value unchanged.

Namespace declarations are excluded from property matching even if a malformed packet attempts to bind the reserved `xmlns` prefix to CRS. A regression ensures such a declaration cannot synthesize an exposure adjustment; normal URI-bound fields remain available.
