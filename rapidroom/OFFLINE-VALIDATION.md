# Offline mode validation plan

Design/evaluation companion to [OFFLINE-MODE.md](OFFLINE-MODE.md), issue #261. **Not executed. No current Offline pass is claimed.** These are future acceptance tests for an implementation; no `--offline` CLI flag currently exists.

## Reproducible setup

Use an owned or redistribution-permitted local photo and an isolated app profile/test user. Do not reuse a personal catalog, live credentials or user model cache. Record source SHA, clean/dirty state, executable SHA-256, bundled WebView/runtime versions, platform, feature flags, configuration hashes and the fixture's permission/provenance. Keep originals read-only and write outputs to a disposable directory. Hash each model and companion asset; record its registry/contract/license status.

Build while holding `/tmp/rapidroom-build.lock`. Still inside that lock, copy the executable and required resources outside the shared target directory to an immutable test location, hash those pinned copies and record their source identity. Verify the copy and manifest before releasing the compile lock; do not leave a copy-after-unlock gap or use mutable resource symlinks. Only afterward acquire `/tmp/rapidroom-gpu.lock` for the runtime stage, using the pinned copies. One stage holds exactly one lock. On the shared development machine require at least 25 GiB free before render stages; remove large rendered outputs after comparison while retaining JSON and useful panels. A concurrent build must not replace the running test binary or its resources.

Start observation **before launching the app**, including Rust, WebView/network subprocesses and resolver activity. Run the matrix in a connected environment: a successful network outage is not proof that the app abstained from requests. Do not change the user's firewall, VPN, DNS or desktop configuration for this test.

Capture both:

- An isolated explicit HTTP(S) proxy log with test-only credentials and a trusted test certificate where necessary, covering browser and Rust requests that honor it. Log host/method/status and counts, not photo contents, tokens or prompts. Record which transports bypass or reject the proxy.
- PID/process-tree-attributed network observation covering direct sockets, DNS (including delegated resolution), WebView processes, retries, redirects and connection attempts. A proxy-only empty log is insufficient. Choose and document an available platform tracer; preflight its ability to observe WebView subprocess traffic and a direct Rust request. Permission or sandbox limitations make the result **inconclusive**, not pass. Keep raw traces private and publish sanitized summaries.

Use positive controls: with the same observation setup and an online test profile, mounting the library should produce the inventory's release-check request. Exercise the same Rust downloader/provider transport against an owned test endpoint where supported by a test harness; never send a private image to a live service for a control. A tracer self-test alone does not establish that a sandboxed WebView is visible. Rebuilds for test instrumentation must be identified separately from the final release binary.

Allow only app assets/IPC, local file/blob operations and the authenticated IPv4-loopback MCP socket. Count provider HTTP to loopback as forbidden. Attribute assistant/browser traffic separately; never subtract an unclassified request just to achieve zero. A denied/failed remote connection attempt or DNS query is a failure even when a proxy/firewall blocks delivery.

Native UI assertions, unit denial tests, proxy evidence and process observation each cover different failure modes; retain all four where applicable.

## Receipt and pass rule

For every run, retain a machine-readable receipt with:

- exact source/base SHA, executable/resource hashes and platform/feature versions;
- profile/policy hashes and active-versus-pending state, fixture permission and local model/companion hashes;
- case ID, timestamps, operation result/refusal, expected/observed request counts and native evidence paths;
- observation tool versions/configuration, process lineage, proxy coverage and direct-socket/DNS coverage, online positive-control result;
- each allowed local connection with reason, each forbidden attempt with owning process/call site, any unattributed traffic, capture gaps and idle duration;
- final `pass`, `fail` or `inconclusive`, with limitations and sanitized artifact hashes.

Pass requires successful positive controls, no unresolved observation gap/unattributed app traffic, zero forbidden attempts and correct local operation/refusal behavior for the exact binary. Any capture failure is inconclusive; any forbidden attempt is fail. Do not replace an absent native/network run with a source-scan result. Publish neither private photos nor raw tokens, prompts, coordinates or personal filesystem paths.
